# Receipt extraction — full-pipeline audit

Date: 2026-09-04 · Against `main` @ 4b27a65 · Scope: capture → upload → queue → extract → normalize → review → financial commit

Findings marked **[proven]** were reproduced by executing the actual extraction
functions (compiled out of `supabase/functions/_shared/receipt-processing.ts`)
against synthetic payloads. Everything else is read from source.

**Revision 2 (2026-09-04, after codex cross-check).** Three claims in revision 1
were wrong and are corrected in place: the RLS scoping in SEV 6, the queue
terminal-failure mechanism in SEV 2, and an unpadded-base64 `RangeError` that does
not occur. Corrections are marked **[corrected r2]**. Two conclusions got *stronger*
under correction — see SEV 2.1 and SEV 2.3.

## 0. The pipeline, end to end

| # | Step | Where |
| --- | --- | --- |
| 1 | User taps capture; image resized/JPEGd | `AddReceiptScreen.prepareReceiptAssetForUpload` (native) / `prepareWebReceiptImage` (web) |
| 2 | Receipt row created `processing_status='uploading'` | `createUploadingReceipt` |
| 3 | Image → `receipts` bucket at `{uid}/{jobId\|tools-inventory}/{receiptId}/{name}` | `uploadReceiptPhoto` |
| 4 | `storage_path` attached | `attachReceiptPhoto` |
| 5 | Row → `queued`, pgmq message sent, all in one txn | `finalize_receipt_capture()` |
| 6 | pg_cron every minute POSTs the worker | `20260608105000_authorize_receipt_worker_cron.sql` |
| 7 | Worker claims ≤3 msgs (300 s visibility), marks `processing`, `attempts+1` | `process-receipt-queue` + `claim_receipt_processing_jobs` |
| 8 | Download image → base64 → OpenAI Responses API (strict JSON schema) | `extractWithOpenAI` |
| 9 | Optional reconciliation retry; optional identity-recovery second call | `processReceiptImage` |
| 10 | Normalize, grade, write receipt row, replace draft line items | `normalizeExtraction` / `getReceiptStatus` / `replaceDraftLineItems` |
| 11 | Activity event + attention item upsert | `recordReceiptProcessedEvent` |
| 12 | Client polls every 2.5 s until `processing_status='complete'` | `ReceiptReviewScreen` |
| 13 | Human assigns lines / whole receipt | `ReceiptReviewScreen` |
| 14 | One atomic idempotent txn writes expenses + audit | `commit_receipt_review()` |

The **spine is genuinely good**: pgmq + visibility timeout, one `for update` lock,
idempotency key + request fingerprint + `last_review_commit_key`, optimistic
`expected_updated_at`, guard triggers that make receipt-derived expenses
unwritable outside the capability, `on delete restrict` from `invoice_expenses`,
a real integration suite. The failures below are almost all in the *interpretation*
and *recovery* layers, not the transaction layer.

## SEV 1 — The number can be wrong and nothing catches it

### 1.1 One hallucinated discount line silently rewrites the printed total, downward **[proven]**

`normalizeExtraction` overrides the model's `total` with
`itemTotal - discountTotal + tax` whenever `discountTotal > 0` and the item lines
match the gross subtotal.

Input: subtotal 1000, tax 70, **printed total 1070**, plus one invented
`INSTANT SAVINGS` discount row of 100.
Result: `total = 970`, `receiptMathReconciles = true`,
`getReceiptStatus = 'accepted'`.

A single spurious discount row moves the receipt total by its own amount and the
math check *confirms* the new number, because the check was computed from the same
line set. Job cost is under-stated by exactly the hallucinated amount.

Mitigation today: `hasReceiptAdjustments` blocks auto-finalize and the UI shows the
"amount paid vs full item prices" choice — but "amount paid" (the wrong 970) is the
primary action. There is no comparison against the model's own printed `total`.

**Fix:** never discard `parsedTotal`. Store both, and if the recomputed total
differs from the printed total by more than tolerance, force `needs_review` with a
message naming the discrepancy. `getReceiptErrorMessage` has no case for this.

### 1.2 Any purchased line containing "card" is silently deleted **[proven]**

`isReceiptSummaryLine` ends with `normalized.includes('card')`.

```
CARDBOARD    -> dropped      Card stock  -> dropped
GIFT CARD    -> dropped      placard     -> dropped
discard bin  -> dropped      2x4 lumber  -> kept
```

Cardboard, card stock, gift cards, placards — all real contractor purchases —
vanish from the line items with no trace. Then item total < receipt total, so
whole-receipt mode is used and the *total* is still right, but the itemization is
wrong and any line-mode split silently loses that cost. Replace the substring test
with anchored patterns (`^menard card`, `^card \d`, `^(visa|mc|amex|debit|credit) `).

### 1.3 A negative item amount becomes a positive charge **[proven]**

`normalizeLineItem` does `line_total: Math.abs(lineTotal)`. A returned item the
model classified as `line_type: 'item'` with `-50.00` is stored as a **+$50 cost**.
`Math.abs` should only apply to `discount` rows; a negative `item` should either be
reclassified as a discount or rejected.

### 1.4 Trailing-minus and parenthesised amounts drop the whole line **[proven]**

The schema allows `line_total` as a string, and the extraction prompt itself
explains that Menards prints `299.57-`. If the model returns the raw string:

```
toMoney('299.57-')  -> null      toMoney('(299.57)') -> null
```

`normalizeLineItem` returns `null` for a null `line_total`, so the **rebate row is
deleted entirely**. Items then exceed the total → the whole receipt drops to
`needs_review` with "line items add up to more than the receipt total", and the
user has no idea the rebate was eaten. `toMoney` needs trailing-minus, leading-minus
and parenthesis handling.

### 1.5 Discounts never reduce job cost in line mode

`commit_receipt_review` forces every non-`item` line to `ignore`
("Tax, fee, discount, and summary lines must be ignored as line expenses") and
computes cost from item lines + allocated tax only. So on a rebate receipt:

- **1 job selected** → the adjustment-choice UI appears. "Full item prices" costs the
  job the *gross* amount, i.e. over-costs by the rebate; `cost_basis='gross_items'`
  records that it happened, but the number is still wrong.
- **2+ jobs, or Tools/Inventory + a job** → `requiresReceiptAdjustmentChoice` is false
  (it requires exactly one job), so `hasUntrustedLineItems` is true, so
  `requiresLineItems` is true, and `handleSave` refuses with *"This receipt needs a
  clean line-item scan before it can be split across multiple jobs."*
  **Hard dead end.** The only exits are delete the receipt or retake the photo.
  This is the exact Menards case the extraction prompt was engineered for.

**Fix:** pro-rate the discount total across assigned item lines (same shape as the
existing tax allocation) instead of discarding it.

## SEV 2 — Receipts can enter states nothing can leave

### 2.1 There is no reaper. `processing_started_at` is written and never read.

Grep confirms: the column is set in `mark_receipt_processing` and read by nothing.
The Tell pipeline got "Prevent Tell queue jobs from hanging" and "queue recovery";
receipts never got the equivalent.

**[corrected r2]** Revision 1 said the worker burns 3 attempts and deletes the
message, stranding the row. The real mechanism is worse: on the hang paths the
attempt counter never increments, so **the terminal branch is never reached and the
message redelivers forever**.

Worker order is: `select receipt` → `mark_receipt_processing` (this is what
increments `processing_attempts`) → `processReceiptImage`. The catch block reads
`processing_attempts` off the row and only goes terminal at ≥ 3. So:

1. If the initial `select` fails, attempts is never incremented. On a fresh receipt
   it reads 0, so `attempts >= 3` is false, the message is *not* deleted, and it
   redelivers every 300 s indefinitely.
2. If `mark_receipt_processing` is blocked by `guard_receipt_financial_state`
   (see 2.3), the same thing — the guard aborts the UPDATE statement, so the
   increment never lands.
3. If the edge function is killed mid-`processReceiptImage` (wall clock), attempts
   *did* increment but the catch never runs, so the terminal check never executes.
   The row stays `processing` and the message redelivers forever.

Consequence: a poisoned receipt permanently consumes a claim slot out of
`maxJobsPerRun = 3` on every run where it is visible, and
`finalize_receipt_capture` returns early for `processing_status in ('queued',
'processing','complete')` so nothing can re-queue it. Meanwhile
`ReceiptReviewScreen` polls every 2.5 s forever (`isReceiptProcessingStatus`
includes `queued`/`processing`), refetching receipt + line items + duplicate
candidates each time, with no ceiling and no "this is taking too long" state.

**[corrected r2]** `finalize_receipt_capture` **already re-queues a `failed`
receipt** (`20260608092000_receipt_processing_queue.sql:87`) — revision 1 implied it
did not. What is missing is a *path to reach* `failed` from a hang, an exposed retry
affordance, and the attempts reset in 2.2.

**Fix:** a lease-aware reclaim job that flips rows with
`processing_status='processing'` and `processing_started_at < now() - interval '15
minutes'` to `failed`; increment attempts *before* the work rather than inside it
so poison always terminates; expose a "Try again" button on the review screen; give
the poll a backoff and a timeout state.

### 2.2 `processing_attempts` is never reset

Once a receipt burns its 3 attempts, any future re-queue is terminal on the first
failure. Reset it in `finalize_receipt_capture` when re-queuing from `failed`.

### 2.3 Reviewing a receipt before extraction finishes poisons the queue job

Nothing prevents a commit while `processing_status` is `queued`/`processing` at the
DB level (the *UI* disables Save, but the RPC does not check). Once the receipt is
`accepted`, `guard_receipt_financial_state` raises on any update from a session that
hasn't set `app.receipt_financial_commit`. The worker never sets it, so:
the worker's own `receipts` update raises → the catch calls `markNeedsReview` →
**that raises too** → attempt fails → 3 attempts → terminal failure → a `danger`
attention item on a receipt that is actually fine.

**[corrected r2]** Revision 1 said this ends in terminal failure plus a `danger`
attention item. It does not — the guard aborts `mark_receipt_processing` *before* the
attempt counter increments, so the message never goes terminal and re-fires every
300 s for the life of the queue.

There is a second consequence revision 1 missed. `commit_receipt_review` never sets
`processing_status` (verified against the migration's UPDATE list), so a receipt
committed while extraction is in flight keeps `processing_status='processing'`
forever. `isReceiptStillProcessing` stays true, and the review screen shows
**"Reading receipt" on a receipt that is already saved and costed** — permanently,
with the 2.5 s poll running behind it.

**Fix:** have `processReceiptImage` re-read `status` and no-op when the receipt is
already `accepted`/`voided`, have `commit_receipt_review` reject a receipt that is
not `processing_status='complete'`, and settle `processing_status` on commit.

### 2.4 A terminally failed receipt shows the user a blank form and no reason

`markNeedsReview` sets `status='needs_review'`, `review_status='needs_review'`.
`ReceiptReviewScreen` renders `error_message` only when
`status === 'error' || review_status === 'error'` (line 110/821). So after three
OpenAI failures the contractor opens the receipt to an empty vendor/date/total form
with no explanation. The message exists — it is only visible in the global activity
feed (`globalActivity.ts:563`). Either set `status='error'` on terminal failure or
widen `needsManualReceiptReview`.

## SEV 3 — Every server-side receipt error is swallowed **[proven]**

`getUserFacingError` shows the real message only if it matches one of 7 allowlist
regexes. None of `commit_receipt_review`'s messages match. Tested 11 of them,
**11/11 replaced with a generic fallback**:

```
SWALLOWED  This receipt changed after it was opened. Reload it and review the latest values.
SWALLOWED  Assigned receipt cost exceeds the amount paid. Choose amount paid or explicitly approve gross item costing.
SWALLOWED  Every authoritative receipt line requires an explicit disposition.
SWALLOWED  A voided receipt cannot be reviewed.
SWALLOWED  Receipt vendor is required.
SWALLOWED  The selected job is not available to this business.
SWALLOWED  You do not have permission to review this receipt.
SWALLOWED  This receipt review was superseded by a newer correction.
SWALLOWED  The amount applied cannot exceed the amount paid.
SWALLOWED  update or delete on table "expenses" violates foreign key constraint ...
```

(Note the near-miss: the allowlist has `/not available for this business/` but the
RPC says "not available **to** this business".)

The user sees "Unable to save receipt. Try again." for a stale-write conflict that
retrying will never fix. All that careful server-side messaging is dead weight.
**Fix:** **not** a deny-list — passing almost every server string through is how raw
constraint text reaches a contractor. Use typed error codes raised by the RPCs
(`errcode`/`hint`, or a `CTX:` prefix on deliberately user-facing messages) and map
them client-side, so anything unrecognised still falls back to the generic message.

## SEV 4 — Data-integrity edges

- **Re-reviewing an invoiced receipt fails with a raw FK error.**
  `commit_receipt_review`, `require_receipt_line_review` and `remove_receipt` all do
  `delete from public.expenses where receipt_id = ...`. `invoice_expenses.expense_id`
  is `on delete restrict`, so the delete is refused — correct for integrity, but the
  error is a Postgres constraint string, and per SEV 3 the user sees "Try again."
  Add an explicit pre-check: *"This receipt is on invoice #1042. Void or edit the
  invoice first."*
- **Whole-mode tax allocation breaks when `subtotal` is null.**
  `v_component_total := coalesce(subtotal,0) + coalesce(tax,0)`. With subtotal null
  and tax 7.00, `allocated_tax = jobCost * 7/7 = jobCost`, so the expense books
  `pre_tax_amount = 0` and the entire amount as tax. Guard on
  `v_subtotal is not null`.
- **No sanity window on receipt dates [proven].** `2099-01-01` and `1999-01-01` both
  pass. The prompt tells the model to ignore return-policy and rebate-expiry dates,
  but there is no code check. A future date lands the expense in the wrong period and
  defeats `receipts_duplicate_lookup_idx (owner_id, receipt_date, total)`. Reject
  `> now() + 1 day` and `< now() - ~3 years`.
- **`toMoney` coercions [proven]:** `toMoney(' ') === 0` (a whitespace `line_total`
  becomes a kept $0 item rather than a dropped line); `toMoney('1.234,56') === 1.23`
  (European format silently becomes $1.23); `toMoney('1e3') === 1000`.
- **`confidence: null` bypasses the per-line confidence gate [proven].**
  `getReceiptStatus` accepts `lineItem.confidence === null || >= 0.6`, and
  `normalizeLineItem` sets `null` for any non-numeric confidence. A model that omits
  confidence gets a free pass. (The top-level `confidence` fails *closed* at 0 —
  correct; make the line-level match.)
- **No cap on line item count [proven].** 5,000 lines normalize and insert fine, and
  each becomes an expense row on commit.
- **Duplicate `line_number` values survive**, so review ordering is nondeterministic
  between polls.
- **Duplicate detection requires an exact date match** and is advisory only —
  nothing prevents committing both copies.

## SEV 5 — Capture layer

- **HEIC on web uploads bytes OpenAI cannot read.** `input.accept = 'image/*'`
  admits HEIC. `prepareWebReceiptImage` decodes via `new Image()`; when the browser
  can't decode HEIC, `readImageDimensions` resolves `{0,0}` and the function
  **returns the original data URL unchanged**, with `mimeType: 'image/heic'`.
  `getFileExtension` then stores it as `.jpg` while `contentType` stays
  `image/heic`. Native is fine (ImageManipulator forces JPEG). Add an explicit
  decode-failure path and reject/convert.
- **Any mid-flow failure orphans a row and possibly a storage object.**
  `processReceiptAsset` runs create → upload → attach → finalize with no resume; on
  failure `step` returns to `'idle'` and a retry creates a *new* receipt and a *new*
  object (`upsert: false` means retrying the same path errors). Orphans stay
  `processing_status='uploading'`, `status='processing'`, and they *do* appear in the
  global activity feed forever. Also `remove_receipt` returns `storagePath` for the
  client to delete afterwards — if the client dies in between, the object leaks.
- **4000 px @ JPEG q0.95** is far beyond typical OCR need. That image is base64'd
  twice (client upload, then again in the edge function) and inlined into the OpenAI
  payload, which drives cost, latency and edge-function memory.
  **[corrected r2]** Revision 1 asserted 1600–2000 px @ 0.8 costs no accuracy. That
  is a *hypothesis*, not a measurement — long thermal receipts with small print are
  exactly where downscaling bites. Build a fixture set of real receipts and benchmark
  extraction accuracy across resolutions before changing the constant.
- ~~**`base64ToArrayBuffer` throws on unpadded base64.**~~ **[corrected r2 —
  withdrawn.]** `new Uint8Array(5.25)` truncates to length 5; it does not raise
  `RangeError` (ToIndex truncates before the SameValue check). The out-of-range
  write in the final loop iteration is a silent no-op on a TypedArray. Neither
  expo-image-picker nor `canvas.toDataURL` emits unpadded base64, so there is no
  real failure here. The decoder could still use an input validation guard, but not
  for the stated reason.

## SEV 6 — Architecture / authorization

- **Authorization is scoped three different ways on the same object. [corrected r2]**
  Revision 1 claimed receipt reads were owner-scoped. That was wrong — it was read
  off `20260518003000_fix_v2_rls_policies.sql` without checking whether a later
  migration superseded it. `20260608095000_business_team_foundation.sql:563` adds
  business-scoped SELECT policies, and because it does not drop the May owner-scoped
  ones, RLS policies OR together. Verified current state:

  | Operation | Effective scope | Defined in |
  | --- | --- | --- |
  | `select` on receipts / line items | `owner_id = auth.uid()` **OR** `user_is_business_member` | May + `business_team_foundation` |
  | `insert` / `update` / `delete` direct | **owner only** — never widened | `fix_v2_rls_policies` |
  | commit / require-lines / remove (RPC) | business — `user_can_manage_business` | `atomic_receipt_review` |
  | receipt **image** in storage | **owner only** — `foldername[1] = auth.uid()`, never revised | `fix_v2_rls_policies` |

  So a business manager who is not the owner can *read* a crew member's receipt and
  *commit* its review through the RPC, but cannot update or delete the rows directly
  and **cannot open the receipt photo at all**. On top of that, every client read
  still hard-filters `.eq('owner_id', userData.user.id)`
  (`fetchReceipt`, `fetchReceiptLineItems`, `fetchPotentialDuplicateReceipts`), so
  today the app behaves owner-scoped regardless — a manager opening a crew receipt
  gets zero rows and `.single()` fails as "Unable to load receipt."
  Four layers, three answers. Pick one model before Business tier ships; the storage
  policy is the one that cannot be papered over client-side.
- **`extract-receipt` is dead code but still deployed.** Nothing imports
  `extractReceipt` (grep: only its own definition). The function runs with
  `verify_jwt = false`, authenticates in-handler, has no rate limit, spends OpenAI
  money per call, takes its Supabase key from a caller-controlled `apikey` header,
  and would race the queue worker (both call `processReceiptImage`, which
  delete-and-reinserts line items). Delete it, or gate it behind an explicit retry
  capability with a status check.
- **Throughput: ~3 receipts/minute in the normal case.** `maxJobsPerRun = 3`, cron
  `* * * * *`. **[corrected r2]** Not a hard ceiling — a long invocation can overlap
  the next cron tick, so real throughput varies.
  Worse, each receipt can make up to 3 sequential OpenAI calls (extraction +
  reconciliation retry + identity recovery), so one invocation can be 9 model calls
  serially — a real wall-clock risk on the edge runtime. A contractor dumping 20
  receipts at the truck waits ~7 minutes. Process concurrently within a run and lift
  the batch size.
- **`status='accepted'` from processing is unreachable.** `getReceiptStatus` returns
  `'accepted'` only when `line_items.length > 0`, and `processReceiptImage`
  immediately downgrades exactly that case to `'needs_review'`. So
  `getProcessedReceiptReviewStatus` can never return `'reviewed'` and
  `getReceiptErrorMessage('accepted')` never fires. Behaviourally fine (everything
  gets human review) but it is dead logic that reads as if auto-accept exists.
- **Auto-finalize commits a financial write with no human approval.** The
  `canAutoFinalizeSingleJobReceipt` effect calls `confirmReceiptLineAssignments`
  automatically. That is a real commit to `expenses`, not a proposal — worth being
  deliberate about against the "AI interprets. Humans approve. Code commits."
  framing in the working context.
  **[r2 note]** codex recommends removing it outright. That is a product decision,
  not a defect finding: the rulebook explicitly allows low-risk actions to graduate
  to "Saved · Undo", and receipts *do* have an undo — `remove_receipt` voids an
  accepted receipt while preserving the image and audit trail. So the shipped
  behaviour may be exactly the intended graduation. What should be decided
  deliberately is whether *silent* commit with no "Saved · Undo" surface counts as
  that graduation, given the SEV 1 defects mean the number being committed is not yet
  trustworthy. Until SEV 1 lands, gating auto-finalize is the conservative call.

## SEV 7 — Test coverage

- `tests/receipt-capture-boundary.test.mjs` and `tests/receipt-integrity-boundary.test.mjs`
  are **regex assertions over source text**. They pass if the file *contains* a
  string. Every SEV 1 bug above is present right now and all 6 tests pass (verified).
  They protect architecture shape, not behaviour, and they break on harmless renames.
- `tests/receipt-integrity.integration.mjs` is genuinely good — real Supabase, real
  commits, covers split/retry/reassignment/rollback, cross-business rejection, the
  credit + gross-choice path, and void-preserves-audit. It does **not** cover the
  queue worker, extraction normalization, or the invoiced-expense delete.
- **`normalizeExtraction`, `getReceiptStatus`, `normalizeLineItems`, `toMoney`,
  `normalizeReceiptDate`, `isReceiptSummaryLine`, `receiptMathReconciles` and
  `lineItemsDoNotExceedReceiptTotal` have zero unit tests.** These eight pure
  functions decide the money. They are trivially testable — extract them into a
  `_shared/receipt-normalization.ts` with no Deno/Supabase imports and put a fixture
  table in front of them. That single change is the highest-leverage item in this
  document.

## Recommended order

Merged with codex's ordering; the two differed only in sequencing, and codex's
"harness first" is right — the fixtures are what keep the SEV 1 fixes fixed.

1. **Extract the eight pure functions into an import-free normalization module and
   land the reproduced cases in this document as fixtures** (SEV 7). Everything
   below is verified by this harness.
2. **Preserve both the model-extracted total and the computed total.** Any
   disagreement beyond tolerance forces explicit review — never a silent overwrite
   (SEV 1.1).
3. Strict money parsing (trailing-minus, parens), `Math.abs` on discounts only,
   anchored summary matching, missing-confidence fails closed, a line-count cap,
   deterministic line numbering (SEV 1.2–1.4, SEV 4).
4. Net discount allocation across assigned items and jobs; unblock the multi-job
   rebate dead end (SEV 1.5).
5. DB guard against committing before processing completes; settle
   `processing_status` on commit (SEV 2.3). **Whether to also remove auto-finalize is
   John's call, not an engineering fix** — see the note in SEV 6.
6. Lease-aware stale-job recovery, attempt reset, terminal-error visibility, poll
   timeout, user-facing retry (SEV 2.1, 2.2, 2.4).
7. Structured user-facing error codes (SEV 3); explicit invoiced-expense pre-check
   (SEV 4).
8. HEIC handling and orphan cleanup, delete the dead `extract-receipt` entry point,
   resolution benchmark, and the authorization decision (SEV 5, SEV 6).
